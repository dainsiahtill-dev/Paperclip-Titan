# Nested executable provenance

## Dynamic boundary

POL-35 and the bounded read-only POL-39 probe observe `/usr/bin/bwrap` as UID/GID 65534 inside the employee tool namespace. The host sees UID/GID 0. Both observations match device 2096, inode 51826, size 72160 and SHA256 `52231e1caf55bcbc667b269f49c63599a6f7db4767ae6a039580d0ff853db712`. Tool `uid_map`/`gid_map` is `1000 0 1`, relative to its immediate parent; its namespace differs from the protected outer payload. These observations do not themselves authorize an ownership exception.

Polaris's Group correctly refuses an unproven binary. Paperclip's remote-only callback bridge authenticates callers, not executable provenance or a guest-verifiable producer. Its READY nonce is explicitly a liveness check. No existing public contract bridges this local boundary safely.

## Proposed bounded contract, pending security review

Paperclip supplies a local **read-only host-facts producer** for the protected run. Polaris consumes authenticated provenance through a KernelOne public bootstrap-bound port. This supplies ownership facts only: it cannot execute commands, grant JobTokens, create project receipts, or settle a project.

- The host producer verifies the canonical installed binary with pinned file descriptors, actual trusted-host ownership, regular-file/link/permission checks and bytes. Only the fixed permitted binary is queryable; no arbitrary path or host-filesystem browse is exposed.
- A local Unix transport must obtain kernel peer identity, pin PID/start/boot and validate the peer belongs to the active protected run, including downstream tool namespaces. Caller JSON, claimed PIDs, environment values and caller-selected descriptors are not identity evidence.
- Open and compare the exact peer-visible canonical binary through the verified peer's filesystem view. A matching original-host file alone is insufficient for overlay, replacement or descendant-namespace cases. Bind the response to peer namespaces, actual host and guest file witnesses, run/company/launch/generation, a fresh request nonce and a narrow lifetime.
- Authenticate producer responses using an established cryptographic implementation and an operator-pinned issuer key. The producer's private key stays outside the guest. A caller-provided key or a mutable environment public key cannot establish trust. KernelOne bootstrap owns issuer admission independently of LLM input; retain existing model bindings.
- The Group consumer preserves canonical-path, regular/link/permission/byte checks and all drift rechecks. It may accept an unmapped ownership view only after authenticating the original root-owned provenance for this exact peer/file. Missing or unsupported provenance fails closed. Do not add a global UID65534 exception, copy/chown a binary, disable sandboxing or substitute a weaker legacy helper.
- Close the producer when the protected owner stops/releases; issue reassignment, expired launch identities and stale process start tokens revoke admission. Retain existing namespace and budget controls.

## Required proof before implementation acceptance

First review the producer anchor, local transport and peer/file binding. Confirm unprivileged host access can collect the required witness for genuine protected tool processes without changing privileges. If kernel/proc access is denied, report that exact boundary; never turn a guest assertion into host evidence.

Positive acceptance requires a real protected employee Group execution with unchanged live source/dependency hashes, bounded outputs and actual cancellation/drain. Negatives cover fake or overlay binaries, nonroot original ownership including other unmapped UIDs, writable links/files, forged/wrong-issuer/wrong-run/stale signatures, replay, changed inode/bytes/permissions, descendant namespace substitution and missing provenance. Observations remain separate from production project-verification authority.

Implementation requires separate exact Paperclip producer and Polaris public-consumer ownership grants. This plan authorizes neither a security bypass nor an unreviewed source change. Fresh Bench remains gated by the actual verifier/authority evidence; no component report counts as native COMPLETED_VERIFIED.

## Independent design review and first access probes

Review retains three implementation gates: issuer admission outside employee-writable source/config; request-level kernel credentials (`SO_PASSCRED`/`SCM_CREDENTIALS`, rather than connect-time `SO_PEERCRED` alone); and unprivileged access to the exact downstream peer view. PID/user namespace ancestry requires the namespace relationship API; mount namespaces must be inspected as exact objects, not invented parent trees. A pidfd alone does not freeze namespace membership or mount contents. Node's standard net interface does not expose the needed Linux credential operation; a reviewed host helper/transport and an established Python verification dependency need separate admission. The current venv lacks cryptography/PyNaCl; no handwritten verification is approved.

Root's readonly host access probe succeeded against the active POL-40 protected payload and namespace init, after matching their exact recorded start tokens. It read the payload's host-view UID map `1000 1000 1` and its root-visible bwrap as actual UID0 with the known file witness. A separate ancestry enumeration found no live nested tool at that instant; 226 denied namespace-parent reads are recorded, not treated as proof that the target's ancestry is accessible. The earlier `heartbeat_run.processPid` probe inspected only the host launcher and is explicitly insufficient for the tool layer.

POL-42 now performs a bounded readonly socket capability experiment. Root's observation-only Unix seqpacket listener uses request-level SCM credentials and reads the exact peer while it waits for a reply. It does not sign facts, modify UID checks, grant execution or qualify Group. The first listener path exceeded the Unix socket length limit; that harness failure is retained and the fresh path is shorter. Any access refusal remains a real boundary.

POL-42 subsequently finished: the genuine readonly tool's single `connect` returned `PermissionError`, errno1/EPERM, before sending a message. No host peer-view witness was collected. Root verified its natural process completion and authenticated namespace release, registered the complete negative observation and stopped only the self-owned empty listener. Source-level diagnosis of the deny and an existing narrowly approved callback path is pending. Do not broaden network access merely to make this probe pass.

Versioned OpenAI Codex 0.160.1 source predicts this precise readonly failure: Restricted network seccomp denies `SYS_connect` while permitting AF_UNIX socket creation. The attribution is source-derived, not a captured POL-42 filter. Linux has no supported path-scoped Unix allowance in that release; macOS-only path settings do not establish Linux support, and the broad dangerous Unix flag is rejected as a solution. Existing command-managed Duplex/stdio framing is a reuse seam, not an exposed local downstream-tool capability or producer authentication.

The readonly result must not be generalized to the engineering execution profile. Paperclip separately configures workspace-write networking for its ordinary engineering roles. A follow-up observation under that existing role configuration may qualify transport without widening the readonly audit role. It still cannot grant binary trust without issuer/sender/file proof, and must respect single-writer admission.

POL-44 succeeded under the existing engineering configuration. Root's stdlib observer received an untruncated SCM credential for actual sender PID72230/UID1000, opened a pidfd, matched start token13817352 before/after, queried its user/PID namespace parents, and opened its exact root-visible bwrap as actual UID0 with the known device/inode/bytes. The source was not changed; the observer handled one request and exited. Root authenticated the employee's subsequent namespace release. This closes engineering transport/access feasibility only; it is not signed provenance or a current-owner admission check.

Independent review admits a narrowly scoped engineering implementation: producer must bind every request to the live host-held owner/run/launch/generation and revoke on stopping/unknown/released; KernelOne must first establish an immutable operator-approved issuer pin and supported verification dependency; Factory must consume only that admitted public port with fresh single-use challenges and all local drift checks. Readonly remains unsupported/fail-closed. No Group UID exception is allowed before the full positive/negative contract passes.

## Conditional mount witness for the existing kernel

The first standalone implementation correctly rejects unavailable unique-mount/statmount support on this WSL kernel. Source review of matching official `linux-msft-wsl-6.6.87.2` identifies a conditional ordinary mount-ID alternative: the kernel reports idmapped flags and retains an ordinary ID until the last actual mount reference is released. Root permits testing this alternative only with both host/peer opened-file mount references held throughout the complete acceptance/consumption lifetime. Namespace FD pins alone are insufficient.

The producer must use its own trusted proc/mountinfo view, join each actual FD's statx mount ID to exactly one row, reject idmapped per-mount options and overlay/unknown filesystem types, validate descriptor filesystem/device/link/permission/byte facts, and reopen both canonical paths immediately before issuance/consumption to compare with the held descriptors. Revocation drains pending operations before releasing pins. Missing or unproved kernel behavior still rejects. Source-tag matching and runtime release strings are not build attestations. Existing failed unique-mount evidence remains preserved; this is not an unconditional fallback or a Group ownership exception.

## Standalone-core security review

The first core records 81 passing component tests but remains unintegrated. Independent review found a blocking sender-contract error: namespace-capable senders may supply an alternate existing visible PID in explicit SCM credentials. The host accurately inspects that referenced process, but its stable witness and uniform threads do not prove it sent the message. This does not imply arbitrary invisible ancestor or cross-project access; the current “actual sender” claim is nevertheless unsupported.

For this transport, SCM identity must be labelled a kernel-validated referenced process and immutable consumer self/thread/namespace/root/file comparison becomes mandatory. A host uniform-thread assertion alone cannot admit it; a separate non-substitution/non-transfer guarantee would need independent proof, which does not exist here. Existing outer cap-drop does not establish that guarantee for every descendant. Add explicit credential-substitution and missing-consumer negatives, preserve the earlier test results, and keep default admission closed until the public consumer/trusted bootstrap is implemented. Connection-time peer credentials alone do not close socket-transfer semantics. Offline signatures also require a defined live lifecycle/consumption contract; deleting host state alone cannot revoke an already delivered signature.
